讲义要求先检查安全性，再处理进程资源请求并执行安全检测；定义Available、Max、Allocation以及Need=Max-Allocation；请求先检查Need，再检查Available，试分配后安全才正式批准。独立银行家算法列在实验四扩充要求中，标为3分。

以下是本项目的安排：主菜单14、预置案例、批量演示、手动输入、逐步Work输出及取消操作。预置数值是项目演示数据，不声称是讲义指定算例。资源用long long非负整数表示；手动界面最多20个进程、10类资源，这是控制录入和表格规模的限制，与分页容量无关。

## 预置安全数据

资源顺序为R0、R1、R2。Available=[3 3 2]，由Available加Allocation列和得到的系统总量为[10 5 7]。

| 进程 | Max | Allocation | Need |
|---|---|---|---|
| P0 | [7 5 3] | [0 1 0] | [7 4 3] |
| P1 | [3 2 2] | [2 0 0] | [1 2 2] |
| P2 | [9 0 2] | [3 0 2] | [6 0 0] |
| P3 | [2 2 2] | [2 1 1] | [0 1 1] |
| P4 | [4 3 3] | [0 0 2] | [4 3 1] |

按程序从P0到Pn-1逐轮扫描的规则，一条安全序列为P1 → P3 → P4 → P0 → P2。Work依次从[3 3 2]变成[5 3 2]、[7 4 3]、[7 4 5]、[7 5 5]、[10 5 7]。安全序列可能不唯一。

批量请求演示均从上表重新开始，不能把上一项批准后的状态当作下一项起点：

| 请求 | 结果 | 原因 |
|---|---|---|
| P1请求[1 0 2] | 获准 | 试分配后仍有完整安全序列，Available成为[2 3 0] |
| P1请求[2 0 0] | 拒绝 | 超过P1剩余需求[1 2 2] |
| P0请求[0 4 0] | 暂缓 | 不超过Need，但R1可用量只有3 |
| P4请求[3 3 0] | 拒绝 | 满足Need及Available限制，但试分配后Work=[0 0 2]，无进程可开始安全序列 |

后三种结果都保持Available、Max、Allocation和推导出的Need不变；界面同时显示请求前后的表格。

## 预置不安全数据

Available=[1 0]，Allocation为P0=[1 0]、P1=[0 1]、P2=[1 0]；Max为P0=[2 0]、P1=[3 1]、P2=[2 1]。系统总量为[3 1]，数据本身合法。

只有P0起初满足Need<=Work，假想完成后Work=[2 0]。P1仍缺R0，P2仍缺R1，无法形成包含全部进程的安全序列。程序将P0标为可完成前缀，而非完整安全序列。

不安全表示不能保证所有进程最终完成，不等于当前就已经发生死锁；安全性检查中的完成和释放只是推演，不改变实际资源表。

## 类关系和关键方法

Banker持有Available、Max、Allocation；Need现场相减，避免请求后忘记同步另一份矩阵。banker_shell.cpp负责输入、输出和演示数据，模型本身不读cin、不访问PCB或MemoryManager。

- initialize：检查维度、非负值、Allocation<=Max、系统资源总量不超long long、单个Max不超过总量。数据合法但不安全也可载入；初始化失败保留旧数据。
- checkSafety：复制Available作为Work，Finish初始全false。找到每类Need都<=Work的未完成者后，假想完成并将Work加上该进程Allocation；一轮无进展即不安全。返回序列及可选逐步记录，整个方法只读。
- requestResources：先检查编号/维度/负值，再逐项检查Request<=Need和Request<=Available。复制当前模型，在副本上扣Available、加Allocation并检查安全；只有安全才整体保存副本，其余情况直接丢弃，避免遗漏回滚。

Work加Allocation的原因：假想先借出Need、完成后归还Need+Allocation，净增的只是原Allocation。这个推演不能被当成真实进程完成，也不是FCFS/SJF/RR的CPU执行序列。

部分请求需要等待时，独立模块只是暂缓本次分配，不修改原进程的阻塞队列。实际表只有获准请求才改变；案例重新载入可恢复初始状态。
